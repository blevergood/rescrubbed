# Protocol and threat model

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._

This document specifies what travels between the hospital and the scoring
vendor, what each side can and cannot learn, and what this design does not
protect against.

---

## 1. The parties

| Party | Holds | Kept private from | Can read the result? |
|---|---|---|---|
| **Hospital** (client) | Patient records (protected health information) | The vendor; anyone observing the network | Yes, sole holder of the decryption key |
| **Scoring vendor** (server) | The trained risk model | The hospital | No, never receives the key |
| **Cloud operator** | The hardware the vendor's server runs on | | No, sees only encrypted data |
| **Care team** | Acts on the risk band | | Yes, part of the hospital |

The hospital will not send patient records to a third party in readable form.
The vendor will not ship its model to every customer hospital.

**Assumed adversary: honest-but-curious.** Each party runs the protocol
correctly and tries to learn what it can from what it legitimately sees.
Section 6 covers what changes if that assumption fails.

---

## 2. Message flow

### Setup, once per key generation

The hospital generates all key material on its own hardware and sends the
vendor only what the vendor needs in order to compute blind.

```
Hospital  --[ encryption context + public key + evaluation keys ]-->  Vendor
```

| File | Size (measured) | Goes to the vendor? |
|---|---|---|
| Public circuit parameters (`circuit.txt`) | < 1 KiB | Yes, both sides hold it |
| Encryption context (parameters) | < 1 MiB | Yes |
| Relinearisation key (needed to multiply) | 48 MiB | Yes |
| Rotation keys (single-patient mode only, 5 of them) | 240 MiB | Yes |
| **Public key (used to encrypt)** | 12 MiB | **Never** |
| **Secret key (used to decrypt)** | 6.5 MiB | **Never** |

Neither the secret key nor the public key crosses the network. The secret key
would let the vendor read the data; the public key it simply has no use for,
since it only computes on ciphertext it is handed and never encrypts anything.
The vendor's home directory is provisioned without either, and the server process exits
with status 2 if a secret-key file is present in its home when it starts.

The hospital needs the ring size, depth and field order to build a matching
context and pack its data. Those values live in `circuit.txt`, which both sides
hold. The weights live in `model.txt`, which only the vendor holds. Given a file
containing weights, a bias, or the band thresholds, the client-side loader raises
an error naming the offending field and stops.

### Per request

```
Hospital  --[ encrypted patient data ]-->  Vendor
Hospital  <--[ encrypted risk band   ]--   Vendor
```

Two request shapes, sharing one model and one band polynomial:

| | Nightly census | Single patient at discharge |
|---|---|---|
| Layout | One ciphertext per field; one slot per patient | All 28 fields of one patient inside one ciphertext |
| Patients per request | up to 32,768 | 1 |
| Upload | 336 MiB | 12 MiB |
| Download | 1 MiB | 1 MiB |
| Per patient | 10.5 KiB | 12 MiB |
| Rotation keys needed | none | 5 |

Nothing else travels between the two hosts.

## 3. What each party learns

### The vendor learns

- **That a request happened**, when, and its shape: a nightly batch or a single
  discharge query.
- **How many patients were in the batch.** Slot occupancy is visible in the
  metadata accompanying the ciphertexts, which reveals census size. Pad to a
  fixed batch size if that matters.
- **Nothing about any patient.** Not the fields, not the score, not the band.
  Every value the server touches is encrypted, including every intermediate. The
  server holds no key.

### The hospital learns

- **The risk band for each patient it submitted**, the intended output.
- **Coarse information about where the band boundaries sit**, accumulated over
  many queries. See section 4.
- **Nothing about the model's internals** from a single query.

### The cloud operator learns

The same as the vendor, minus the model, assuming the vendor deploys it
encrypted-at-rest or the operator is inside the vendor's trust boundary. A vendor
running its plaintext model on rented hardware is exposed to its own supplier,
which is outside the scope of this design.

## 4. Output privacy

Encrypted computation protects the inputs. The answer is a separate question.

### Recovering the model from exact scores

The model is a weighted tally over 28 fields. Were the server to return the exact
score, the hospital could:

1. Submit 29 fabricated patients with chosen field values.
2. Receive 29 exact scores.
3. Solve 29 linear equations in 29 unknowns (28 weights and a bias).

No encryption is broken in that sequence. Returning a probability instead of a
score changes nothing, being an invertible relabelling of the same number.

### What the service returns instead

The server computes the risk band inside the encrypted computation and returns
only that: `0` low, `1` moderate, `2` high. Each answer carries about 1.6 bits.

Both established bedside scores, LACE and HOSPITAL, band patients rather than
reporting a number. The care decision they feed is binary: enrol this patient in
a transitional-care programme, or do not.

### What banding leaves open

A hospital willing to spend queries can still recover the model's shape:

- Vary one field while holding the rest fixed, and binary-search for the value at
  which the band flips. That locates a point on a band boundary.
- Repeating this recovers the ratios between weights, and enough boundary points
  recover the boundary itself.
- Published estimates put the cost at order 10²–10⁴ queries depending on the
  precision sought, against 29 for the exact-score design.

The deployment therefore needs query rate limiting, per-customer budgets, and
audit logging. These are operational controls rather than cryptographic ones, and
the extraction bound above holds only while they are enforced.

### Other output channels considered

- **Patient re-identification from the output.** The hospital already holds the
  record it submitted.
- **Inferring the vendor's training data** from outputs. Banding reduces the
  channel without closing it. This is standard machine-learning exposure,
  unchanged by encryption.
- **Timing and size side channels.** The computation is data-oblivious: the
  identical sequence of operations runs regardless of the values, so timing
  reveals batch size, which is already visible.

---

## 5. Output integrity

The party that decrypts (the hospital) is the same party that acts on the result
(its care team). No third party has to be convinced the result is genuine, so
the design carries no transciphering layer or signature scheme.

## 6. Threats this design does not address

1. **A malicious vendor.** Encryption guarantees the vendor cannot read the data.
   It does not guarantee the vendor computes the right thing. A dishonest vendor
   could return "low risk" for everyone, and the hospital could not detect it
   cryptographically. *Mitigation:* submit canary patients with known expected
   bands at random intervals and check them.

2. **A malicious hospital.** The rate limiting in section 4 is an operational
   control the vendor has to enforce. A hospital that can issue unlimited queries
   can eventually extract the model.

3. **Exhaustive querying.** Covered above. The defence is a query budget.

4. **Side channels on the vendor's hardware.** Power analysis, cache timing, and
   memory-bus probing against the server process are out of scope. Encrypted
   computation does not defend the machine it runs on.

5. **Compromise of the hospital's secret key.** Everything rests on that one
   file. If it leaks, every ciphertext ever sent becomes readable to whoever
   holds it, including any the vendor retained. *Mitigation:* standard key
   custody, and periodic key rotation to bound the exposure window.

6. **Traffic analysis.** An observer learns when scoring runs happen and how
   large the census is, without reading anything.

7. **Repeated key use.** Reusing one key pair across runs is cryptographically
   sound here. A known weakness in this family of schemes (Li–Micciancio) applies
   when an attacker can observe decrypted results of computations it influenced.
   The vendor never sees any decryption. That property would need re-examining if
   decrypted outputs were ever shared back to the vendor.

8. **The quality of the model itself.** This design reproduces the reference
   model. That model reaches a ranking quality of 0.651 against a 0.659 ceiling
   measured on the same features; roughly 21% of the patients it flags as
   high-risk are readmitted, against an 11.6% background rate. See
   [`../reports/results.md`](../reports/results.md).

## 7. Coverage

Polynomial stand-ins for sharp comparisons are valid only over the range they
were fitted to, so encrypted designs commonly reject inputs falling outside it.
This design rejects no patient.

Before encrypting, the client clips each field to a published clinical range
(`data/feature_bounds.csv`) and maps it to 0–1. Every field is then within 0–1
and the weights are fixed, so the score is confined to **[-4.18, +1.65]** by
arithmetic over the input contract rather than by observation of a sample. The
polynomial is fitted over that interval plus a 2% margin.

Consequences:

- **Reject rate: zero.** Every patient gets a band.
- The composition question ("does the rejected set over-represent the patients
  you care about?") does not arise, because nothing is rejected.
- One out-of-range record would otherwise spoil all 32,768 patients in a batch,
  which decrypts as a unit.

`feature_bounds.csv` contains input ranges only, no weights, so publishing it to
clients discloses nothing about the model. The ranges are clinical values such as
a length of stay between 1 and 14 days.

The residual effect is clipping. A patient with an extreme value is scored as
though they sat at the boundary, so a 20-day stay is scored as 14 days. These
fields are continuous clinical counts, where a value held at the bound still
carries the ordering the model uses. No categorical field is clipped; all are
already 0 or 1.
